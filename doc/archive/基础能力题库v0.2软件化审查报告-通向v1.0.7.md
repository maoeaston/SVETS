以下结论以本轮上传的 `PRD v1.0.6-scoring-closure`、`schema.sql v0.1.10-scoring-closure`、题库与资源 Mini-PRD、JSON 类型定义，以及《通用基础能力正式测评候选题库 v0.2 软件优先版》为基线。

有一个审查边界需要先声明：你上传的 PRD v1.0.6 是“增补/替换版”，多处写明其余章节沿用 v1.0.5，但本轮没有提供 v1.0.5 全文。因此，涉及未展开章节的判断标记为 `[需确认]`。

## 1. 总体结论

* 当前 PRD 是否可以继续开发：**需要小修**
* 是否需要暂停重构：**不需要暂停底层架构重构**
* 是否建议先改 PRD 再继续写代码：**建议先完成一次题库数据合同补丁，再继续 5.3 真实题库导入、评分器和交互组件编码**

当前 `schema.sql` 已通过 SQLite 全量初始化验证，可正常创建 20 张表和 44 个触发器。事件溯源、会话、结果投影、安全事件、题目冻结、线下双轨评分等底层结构可以继续保留，不需要推翻。

### 最大风险

最大风险不是 SQLite 表不够，而是：

> **新题库已经从“传统题目”变成了“行为任务集合”，但当前系统仍把所有线上内容压缩成判断、单选、拖拽三种答题模型，并强制每条线上记录只能得到 0/2 分。**

由此产生四个阻断性问题：

1. 新题库包含多选、轨迹控制、多点触控、计时等待、持续任务、音频多步执行、分支沟通、多步骤模拟等交互，现有四类题型无法稳定表达。
2. 新题库明确要求 `NR/ST`，即不适用、未施测或安全停止不能直接记 0；当前 `answer_record` 和 `offline_score_record` 都强制必须写分数。
3. 96 个候选条目中有 1 个“跨任务系统派生观察指标”，明确不是独立题目、不应单独计分；当前结构没有“计分题/观察项”的区分。
4. 候选题库仍处于内容效度复核和试测阶段，但 PRD 已经允许输出等级和就业安置建议。教师复核门禁降低了风险，但没有解决“题库尚未验证”的测量学前提。

新题库共 96 个候选条目，包括 87 个纯软件条目、1 个软件嵌入日志观察项和8个必要实物条目；设计原则明确要求将不同证据类型分开解释，并避免把图片选择等同于真实动作能力。

### 建议开发边界

可以继续开发：

* 学生档案。
* strategy_config。
* 资源登记。
* 导入 dry-run。
* DRAFT 题库导入。
* 题目审核报告。
* 现有会话与事件底座。

应暂缓：

* 将这批题批量转为 `ACTIVE`。
* 按现有 14 判断 + 14 单选 + 14 拖拽组卷。
* 对复杂软件任务直接套用 `SINGLE_CHOICE` 或 `DRAG`。
* 正式输出安置方向。

## 3. 题型与交互类型审查

### 3.1 可以映射到现有题型的内容

可以继续使用现有题型：

* 二元行为判断：`TRUE_FALSE`
* 单一答案图片或文字选择：`SINGLE_CHOICE`
* 简单一对一匹配：`DRAG`
* 图片分类：`DRAG`
* 图片排序：可暂时使用 `DRAG`，但必须增加排序答案合同
* 线下标准实操：`OFFLINE_OPERATION`

### 3.2 无法良好映射的内容

以下任务不应强行伪装成 `SINGLE_CHOICE` 或 `DRAG`：

* 从 8 张图片中选择 2 张目标图片。
* 连续描线、沿路径滑动。
* 无自动吸附的精细放置和堆叠。
* 一只手按住、另一只手拖拽的多点触控。
* 延迟 10 秒后的记忆提取。
* 连续 3 分钟数字分拣。
* 随机停止指令和停止反应时延。
* 模糊指令后的澄清请求。
* 状态汇报、求助、休息告知。
* 有前后节点的分支情境。
* 计时等待、返回任务、恢复与交接。
* 从其他题目事件派生的跨任务观察指标。

候选题库已经明确包含点击、拖拽、排序、音频指令、分支交互、计时等待和系统日志，不是传统三类线上题可以完整覆盖的。

### 3.3 是否需要新增 `interaction_type`

**需要，MVP 必须新增。**

同时建议只新增一个新的数据库级 `question_type`：

```ts
type QuestionType =
  | 'TRUE_FALSE'
  | 'SINGLE_CHOICE'
  | 'DRAG'
  | 'SOFTWARE_TASK'
  | 'OFFLINE_OPERATION'
```

`question_type` 表示存储和评分大类；`interaction_type` 表示渲染器和答案形状。

### 3.4 推荐 interaction_type

| interaction_type | question_type     | answer_shape                               | MVP 自动评分   |
| ---------------- | ----------------- | ------------------------------------------ | ---------- |
| `BINARY_SELECT`  | TRUE_FALSE        | `{ selected: boolean }`                    | 精确匹配       |
| `SINGLE_SELECT`  | SINGLE_CHOICE     | `{ selected_option_id: string }`           | 精确匹配       |
| `MULTI_SELECT`   | SOFTWARE_TASK     | `{ selected_option_ids: string[] }`        | 集合匹配或阈值    |
| `DRAG_DROP`      | DRAG              | `{ placements: [{item_id, zone_id}] }`     | 映射匹配       |
| `ORDERING`       | DRAG              | `{ ordered_item_ids: string[] }`           | 完全顺序或结构化阈值 |
| `GESTURE_TASK`   | SOFTWARE_TASK     | `{ outcome, metrics }`                     | 指标阈值       |
| `TIMED_TASK`     | SOFTWARE_TASK     | `{ actions, metrics, final_state }`        | 事件条件 + 阈值  |
| `TASK_SEQUENCE`  | SOFTWARE_TASK     | `{ completed_steps, step_order, metrics }` | 必要步骤和顺序    |
| `BRANCHING_TASK` | SOFTWARE_TASK     | `{ path, messages, final_state }`          | 必要节点、行为和终态 |
| `OFFLINE_RUBRIC` | OFFLINE_OPERATION | 教师评分记录                                     | 不自动判分      |

其中 `GESTURE_TASK` 可通过 `interaction_subtype` 区分：

```ts
type GestureTaskSubtype =
  | 'TRACE_PATH'
  | 'PRECISION_PLACEMENT'
  | 'CONTINUOUS_SLIDE'
  | 'MULTI_TOUCH_HOLD_DRAG'
```

`BRANCHING_TASK` 可通过 subtype 区分：

```ts
type BranchingTaskSubtype =
  | 'FUNCTIONAL_COMMUNICATION'
  | 'CLARIFICATION_REQUEST'
  | 'HELP_REQUEST'
  | 'STATUS_REPORT'
  | 'BREAK_NOTIFICATION'
  | 'SAFETY_RESPONSE'
```

### 3.5 热点点击是否需要

**当前材料不足以证明 MVP 必须增加独立的 `HOTSPOT` 类型。**

现有题目主要是点击独立图片卡片，不是必须在一张复杂图片中点击坐标区域。因此：

* 图片卡片目标点击：用 `SINGLE_SELECT` 或 `MULTI_SELECT`
* 单张图片内部区域识别：Post-MVP 再增加 `HOTSPOT_SELECT`
* 当前不建议为了预留而实现图片标注编辑器

### 3.6 实现边界

数据合同应当现在就能表达全部候选题，但渲染器可以分批实现：

* 已实现 interaction_type 的题目可以审核转 `ACTIVE`
* 未实现的题目保持 `DRAFT`
* 上线门禁只统计“内容审核通过 + 资源有效 + 交互已实现”的题目
* 不允许通过把复杂任务降级成单选来凑足 42 题

### 4.4 item_usage 建议

建议在 `question_bank` 新增：

```sql
item_usage TEXT NOT NULL DEFAULT 'SCORED_ITEM'
CHECK (item_usage IN (
  'SCORED_ITEM',
  'OBSERVATION_ONLY'
))
```

MVP 只需要两个值：

* `SCORED_ITEM`：可以参与 42+8 组卷
* `OBSERVATION_ONLY`：不能进入题量统计和分数计算，只能从事件派生报告指标

新题库中的“恢复与交接跨任务观察”明确属于 `OBSERVATION_ONLY`，不应被算作第 43 道线上题，也不应得到 0/2 分。

`TRAINING_ONLY`、`FINAL_EXAM_ONLY` 暂不引入，留到 Post-MVP。

### 4.5 expected_answer 的唯一事实源

当前 TypeScript 把 `expected_answer` 放在 `content_json`，而 `scoring_rule_json` 只描述“精确匹配”，容易形成两个事实源。

建议改为：

* `content_json`：只保存呈现、选项和交互
* `scoring_rule_json`：保存 expected answer、通过阈值和评分逻辑

不要在两个 JSON 中重复正确答案。

```json
      "operator": "LTE",
      "value": 1
    }
  ],
  "pass_score": 2,
  "fail_score": 0,
  "scoring_engine_version": "1.0.0"
}
```

分支任务：

```json
{
  "schema_version": "scoring-rule-v1.1",
  "scoring_type": "EVENT_RULE",
  "logic": "ALL",
  "required_events": [
    "TASK_PAUSED",
    "CLARIFICATION_REQUESTED"
  ],
  "forbidden_events": [
    "EXECUTED_WITH_MISSING_INFORMATION"
  ],
  "allowed_terminal_states": [
    "CLARIFIED_AND_COMPLETED"
  ],
  "pass_score": 2,
  "fail_score": 0
}
```

不要在 JSON 中放任意 JavaScript 表达式。使用固定的 `metric + operator + value` 白名单，避免判分脚本执行任意内容。

### 4.7 当前 TypeScript 类型需要立即修正的冲突

当前 `03-json-schemas.ts` 存在以下明确不一致：

1. `ContentJsonDrag.scoring_mode` 允许 `PARTIAL_CREDIT`，但 PRD 明确线上只能 0/2。
2. `ScoringRuleDrag` 名为 `DRAG_PARTIAL`，但 `partial_correct_score` 又固定为 0。
3. `ScoringPolicyJson.score_values` 固定为 `[0,1,2]`，没有区分线上 `[0,2]` 和线下 `[0,1,2]`。
4. `ScoringPolicyJson.level_rules` 与 strategy_config 表级阈值重复，可能产生两个等级事实源。
5. `QuestionPolicyJson.question_ratio` 名称叫 ratio，seed 实际存储的是 14、14、14、8 的数量。
6. 类型定义没有 `interaction_type`、证据类型、支持策略、效度边界、NR/ST 和报告合同。

这些类型目前只能承载传统题，不能稳定承载软件优先候选题库。

### 4.8 变体处理

MVP 建议：

* 不使用 `content_json.variants[]` 随机切换不同答案或不同难度。
* 每个有实质差异的变体建立独立 `question_id`。
* 用 `variant_group_id` 表示同源平行题。
* 题目修订继续使用 `superseded_by_question_id`。
* 只有纯视觉等价、答案完全相同的随机素材，Post-MVP 才考虑嵌套 variant。

这样可以避免还要在 `assessment_session_question` 中增加随机 variant 复现机制。

## 5. 评分规则审查

### 5.1 线上 0/2、线下 0/1/2 是否足够

结论：

* 作为 **MVP 最终成绩值域**，基本足够。
* 作为 **行为证据记录模型**，不够。
* 不建议本轮恢复线上 1 分。
* 必须保存原始指标、响应状态和支持等级。

### 5.2 自然具有部分完成状态的题目

以下任务虽然最终仍可输出 0/2，但必须保留细粒度指标：

* 12 项分类中完成 10 项。
* 6 个图形中匹配 5 个。
* 三步指令完成 2 步。
* 多选题选中部分目标但存在误选。
* 流程排序只有相邻一步错误。
* 描线完成但部分越界。
* 持续任务中完成量合格但出现长时间空闲。
* 安全处理完成停止和求助，但漏掉上报对象。

MVP 处理方式：

```text
细粒度表现 → answer_payload_json.metrics
结构化阈值判定 → scoring_rule_json
最终线上成绩 → 2 或 0
```

不要把“正确了几项”直接转成 1 分，否则重新打开了 PRD v1.0.6 已经关闭的线上三档评分问题。

### 5.3 支持等级 P0/P1/P2/P3

支持等级和无障碍合理便利必须分开记录。

#### 无障碍合理便利

例如：

* AAC
* 触控笔
* 助听设备
* 日常视觉辅具
* 非关键字体放大
* 非关键音量调整

这些不等于提示，不应自动降分。

#### 提示等级

| 等级 | 定义                  | 是否可自动评分         |
| -- | ------------------- | --------------- |
| P0 | 标准指令，无额外提示          | 是               |
| P1 | 按规则完整重复一次指令，或非答案性澄清 | 题目允许时可以         |
| P2 | 提供过程性提示，但不直接给出答案    | 由题目规则决定，通常需教师复核 |
| P3 | 直接指出关键答案、代操作或手把手协助  | 不应作为独立完成成绩      |

必须记录支持等级的题型：

* 所有 `SOFTWARE_TASK`
* 所有 `OFFLINE_OPERATION`
* 音频指令题
* 计时任务
* 分支沟通题
* 情绪和社交行为任务
* 安全操作题

简单判断和单选题也应默认写 `P0`，使用额外支持时写实际等级。

### 5.4 只能由教师补录的内容

* 8 道必要实物题的 0/1/2 rubric。
* 疼痛、明显疲劳、吞咽、夹伤、跌落等终止原因。
* 实际使用的日常辅具。
* P2/P3 支持是否破坏目标构念。
* 设备故障还是学生未完成的判定。
* 口语、手势或 AAC 中无法由软件确定语义的开放表达。
* 跨任务恢复与交接的嵌入观察。
* 安全相关专业判断。
* 教具规格发生变化时的版本说明。

8 道必要实物任务包括 7 道手部操作及 1 道轻箱搬运；题库已经明确其材料、教师准备动作、替代方案和效度边界。

### 5.5 只能进入行为日志、不能直接等同成绩的指标

除非某道题的 `scoring_rule_json` 明确将其定义为目标构念，否则以下指标不得直接算分：

* 反应时间。
* 总完成时间。
* 拖拽速度。
* 轨迹长度。
* 离手次数。
* 点击修改次数。
* 自我纠正次数。
* 重播次数。
* 请求帮助次数。
* 休息请求。
* 空闲时长。
* 情绪恢复时间。
* 沟通方式。
* 是否使用 AAC。
* 是否使用触控笔。
* 惯用手。
* 行为外显程度。
* 速度快慢。

例如“规则坚持”题中，低速度不等于不坚持；候选题库已经明确要求将速度和持续参与分开报告。

### 5.6 NR/ST 与分数的关系

必须区分：

| response_status          | 含义                | score       |
| ------------------------ | ----------------- | ----------- |
| `ANSWERED`               | 正常提交              | 0/2 或 0/1/2 |
| `NOT_APPLICABLE`         | 因运动、视觉、听觉、沟通条件不适用 | NULL        |
| `STOPPED_SAFETY`         | 因疼痛、疲劳或安全风险停止     | NULL        |
| `TECHNICAL_INTERRUPTION` | 设备或素材故障           | NULL        |
| `ASSISTED_NOT_SCORED`    | P3 直接协助后完成        | NULL        |

候选题库明确要求，因运动、视觉、听觉或沟通限制导致不适用时应记录 NR，不得直接记 0。

需要与 PRD 的“中途终止未答计 0”区分：

* **session 因崩溃或红线整体终止后未到达的题目**：按 PRD 未答计 0。
* **已经到达但题目不适用、设备故障或安全停止**：记录 NR/ST，不应伪装为错误答案。
* 存在预先批准的同构替代题时，应在组卷前替换。
* 没有替代题时，`completion_ratio < 1`，不得输出安置建议。

## 7. 素材与资源结构审查

### 7.1 MVP 必须支持的素材

* `IMAGE`
* `AUDIO`
* 线下教具说明/清单
* 可选的 `PDF` 工具清单
* 本地 UI 图标和背景素材

当前新题库的主要线上素材是：

* 场景图片。
* 物品图片。
* 图卡。
* 轮廓和目标区。
* 行为步骤卡。
* 音频指令。
* AAC 消息卡。
* 计时器和任务状态。

### 7.2 Post-MVP 素材

* 视频情境题。
* Lottie 或复杂动画素材。
* 可编辑热点图。
* 语音采集和自动语义判分。
* 摄像头或姿态识别数据。
* 自适应分支脚本包。

### 7.3 当前资源结构的缺口

1. schema 注释仍举例 `app://assets/video/...`。
2. Mini-PRD 和当前代码口径是 `app://asset/<asset_id>`。
3. `media_asset_id` 有正式外键，但 content_json 中的子素材 ID 没有数据库外键。
4. 题目冻结后，`asset_resource.file_hash/local_path/app_uri` 仍可能被原地更新。
5. 如果同一个 asset_id 的文件被覆盖，历史题目虽然被冻结，历史呈现仍然不可复现。

### 7.4 避免题目和图片一改就返工

执行以下规则：

1. 题目只引用 `asset_id`，不引用绝对路径。
2. `asset_id` 使用稳定、可读、带版本的编号：

   * `AST_GA_COG_001_SCENE_V1`
   * `AST_GA_COG_001_OPTION_A_V1`
3. 已被 ACTIVE 或历史题目引用的资源不得覆盖文件内容。
4. 图片修改必须创建新 asset_id。
5. 修改题目素材引用时，新建题目版本并走 `superseded_by_question_id`。
6. `file_hash` 必须是内容 hash，不以文件名判断一致性。
7. 每个素材声明语义角色：

   * `SCENE_IMAGE`
   * `OPTION_IMAGE`
   * `DRAG_ITEM_IMAGE`
   * `BACKGROUND_IMAGE`
   * `VOICE_PROMPT`
   * `OFFLINE_TOOL_GUIDE`
8. 所有 JSON 中的 asset_id 在转 ACTIVE 前由 validator 扫描验证。
9. 不允许 renderer 直接读取 `local_path`。
10. 统一使用 `app://asset/<asset_id>`。

本轮不必新增完整 `question_asset_binding` 表。现有 `asset_resource + JSON validator + ACTIVE 门禁` 足以完成 MVP。若后续需要在数据库层查询“一张图片被哪些题引用”，再将绑定表放入 Post-MVP。

### 8.1 当前结构是否能承载

* 证据类型被混成单一模块分数。

### 8.3 报告必须遵守的解释边界

* 情境判断题只能解释为风险识别或流程认知。

* 嵌入观察项不能进入 100 分总分。

```json
{
  "placement_advice_enabled": false
}
```

等完成专业复核、可用性测试和小样本试测后：

* 新建 strategy version。
* 将 `placement_advice_enabled` 改为 true。
* 不修改已有策略版本。

`task_report` 现有 placement review 门禁可以保留。

2. `question_bank.question_type` 增加：

```sql
'SOFTWARE_TASK'
```

同步修改：

* `assessment_session_question.question_type`
* `answer_record.question_type`

3. `question_bank` 增加：

```sql
item_usage TEXT NOT NULL DEFAULT 'SCORED_ITEM'
CHECK (item_usage IN ('SCORED_ITEM', 'OBSERVATION_ONLY'))
```

4. `answer_record` 增加 `response_status`，并允许非正常状态下 `score IS NULL`。

5. `offline_score_record` 增加相同的 `response_status`，并允许 NR/ST 时 `score IS NULL`。

6. 给 `answer_record` 增加“答案必须属于本 session 已选题目”的保护。推荐使用复合 FK 或触发器校验：

```text
session_id + question_id 必须存在于 assessment_session_question
question_type 必须一致
question_phase 必须为 ONLINE
```

7. 给 `offline_score_record` 增加触发器：

```text
OFFLINE_ABILITY 的 question_id 必须属于本 session
question_type 必须为 OFFLINE_OPERATION
question_phase 必须为 OFFLINE
```

目前 schema 只校验 question_id 非空，没有校验题型和 session 归属。

8. 给 `assessment_session_question` 增加选题门禁：

* 题目创建 session 时必须为 ACTIVE。
* `item_usage='SCORED_ITEM'`。
* 题目 `job_code` 与 session 一致。
* module_type、question_type 与 question_bank 一致。
* OFFLINE_OPERATION 只能进入 OFFLINE phase。
* 其他题型只能进入 ONLINE phase。

9. 扩展题目冻结字段：

当前触发器还应冻结：

* `job_code`
* `item_usage`
* `safety_sensitive`
* `sensory_tags_json`
* `variant_group` 所在内容

10. 增加 supersede 联动约束：

```text
superseded_by_question_id 非空时，旧题 status 必须为 ARCHIVED
```

11. 对 `result_record` 增加服务层或 trigger 验收：

```text
result_type='ABILITY_SCORE' 时 completion_ratio 不得为空
```

12. 更新 schema 中 app URI 注释为：

```text
app://asset/<asset_id>
```

### 9.5 导入脚本修改

将 v0.2 源表字段映射为：

* 题目ID → `question_id`
* 模块 → `module_type`
* 子维度 → `sub_module`
* 呈现方式 → `presentation_type`
* 交互类型 → `interaction_type/subtype`
* 预期难度 → `difficulty_level`
* 目标构念 → `target_construct`
* 测评任务、标准施测指令 → presentation
* 达标行为、核心评分点 → scoring rule 和 observable indicators
* 允许的标准支持 → support policy
* 终止/安全条件 → termination policy
* 系统记录指标 → log_metrics
* 证据类型 → evidence_type
* 效度边界 → validity_boundary
* 来源追溯、调整方式 → source
* 需专业确认 → professional_review

特殊规则：

* 跨任务系统观察项导入为 `OBSERVATION_ONLY`。
* 不可识别 interaction_type 的题保持 DRAFT。
* 需要专业确认但未确认的题保持 DRAFT。
* 资源缺失的题保持 DRAFT。
* 评分规则无法二值化的线上题保持 DRAFT。
* 不允许导入脚本为了凑题量伪造素材或答案。

### 9.6 新增验收标准

1. 新导入题默认状态必须为 DRAFT。
2. 96 个源条目导入后，应识别出 1 个 `OBSERVATION_ONLY`。
3. `OBSERVATION_ONLY` 不得进入 assessment_session_question。
4. `OBSERVATION_ONLY` 不得生成 answer_record 和分数。
5. 未实现 interaction_type 的题不得转 ACTIVE。
6. 图片多选能保存多个 option ID。
7. SOFTWARE_TASK 线上分数只能是 0 或 2。
8. 所有判分指标均能在 answer_payload 中复现。
9. P0/P1/P2/P3 与 accommodations 分开保存。
10. AAC、触控笔等合理便利不能自动扣分。
11. NR、ST、技术中断允许 score 为 NULL。
12. 设备故障不能写成错误得 0。
13. answer_record 的题目必须属于当前 session。
14. question_type 与 session question 必须一致。
15. OFFLINE_ABILITY 评分只能关联本 session 的 OFFLINE_OPERATION。
16. 题目进入 session 时必须为 ACTIVE。
17. 专业确认未完成的安全题不得转 ACTIVE。
18. asset hash 变化后不得覆盖已引用 asset_id。
19. 新素材必须使用新 asset_id。
20. 报告按五类 evidence_type 分开展示。
21. 嵌入观察指标不得进入总分。
22. 试测 strategy 不输出就业安置方向。
23. NR/ST 存在时 `completion_ratio` 和报告限制正确。
24. 线上任意路径不得产生 1 分。
25. 现有 session、安全事件、结果投影回归测试必须继续通过。

### 9.7 不建议本轮做

* 完整题库管理后台。
* 可视化题目编辑器。
* 可视化分支流程设计器。
* 公共模拟卷和自定义试卷库。
* 固定结业卷后台。
* 自适应测验。
* IRT、常模和项目参数系统。
* 原始 pointer trace 独立分析表。
* 眼动、摄像头和姿态识别。
* 语音 NLP 自动判分。
* 热点图片编辑器。
* 自动从 PDF、Word 抽题。
* `scoring_rule` 公共规则表。
* `question_asset_binding` 表。
* ORM。
* CSV 解析库。
* Markdown 报告渲染库。
