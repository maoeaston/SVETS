请基于当前“炫灿-职途向导系统”工程基线，对“方案 B：Electron 内嵌本地服务 + 教师平板浏览器 + 学生触摸一体机”进行一次面向长期产品演进的正式架构审查，并形成可执行的架构设计与变更建议。

本次不要以“MVP 最小改动”为首要目标，也不要因为当前只有一台一体机和一台教师平板，就把数据结构、接口或业务流程写死。需要保证该架构未来可以支撑：

* 多台学生触摸终端；
* 多名教师和多个教师平板；
* 学生正式账户体系；
* 学生观看教学视频、完成学习任务和训练任务；
* 学生查看个人测评记录、学习记录和训练记录；
* 教师发起测评、实时查看进度、暂停、恢复和终止；
* 学生线上作答后继续进行线下实操；
* 教师在平板上查看线下题目、观察点、评分锚点并直接评分；
* 局域网断线、终端刷新、Electron 重启后的会话恢复；
* 学校级本地服务器或未来中央服务端同步；
* 现有安全红线、事件溯源、结果投影和报告保护规则。

当前技术与业务基线：

* Electron + Vue 3 + TypeScript + SQLite；
* 当前不引入 ORM；
* SQLite 继续作为本地权威数据库，不要为了双端协同直接改成 PostgreSQL；
* `action_log.jsonl` 是事实事件来源，SQLite 是查询和业务投影；
* UI 不得直接修改业务状态，所有状态变化必须经过领域命令、状态机和事件；
* 测评结果、训练结果、实操结果禁止混算；
* 安全红线优先级最高；
* `REDLINE_HALTED`、`COMPLETED`、`ABORTED` 等终态不可逆；
* 学生端不得收到 `expected_answer`、正确答案标识、教师评分锚点或完整评分规则；
* 学生必须拥有长期正式账户，不能因为当前受教师主持就取消学生账户体系。

请首先纠正以下不严谨描述：

“学生一体机跑 Electron，Kiosk 模式免登录自动进入答题。”

正确语义应当是：

“学生一体机启动后自动进入受控的学生工作站外壳，但不能自动冒充任何学生。正式进入测评、学习或训练前，必须建立明确的学生设备会话，并关联学生账户、设备、教师授权和具体业务会话。”

需要明确区分以下对象：

1. 长期学生账户；
2. 教师账户；
3. 设备身份；
4. 设备登录会话；
5. 教师辅助发起的学生受限会话；
6. 学生自主登录会话；
7. 测评会话；
8. 训练会话；
9. 学习任务会话；
10. 设备与业务会话的临时分配关系。

请按以下原则设计方案 B。

一、进程与模块边界

不要简单地把 Fastify/Express 路由、SQLite 操作和业务逻辑全部堆进 Electron 主进程。

建议评估以下结构：

* Electron Main：窗口、Kiosk、进程监管、系统能力和升级；
* Local Application Server：HTTP、WebSocket、认证、命令调度和资源服务；
* Application/Domain Layer：状态机、权限、事务、评分、安全红线和事件生成；
* Infrastructure Layer：SQLite Repository、action_log、文件资源、备份和同步适配器；
* Student Renderer：学生工作站界面；
* Teacher Web：教师平板浏览器界面。

优先考虑将 Local Application Server 设计为可独立运行的 TypeScript 模块，并由 Electron 通过 `utilityProcess` 或子进程启动和监管。需要说明采用同进程、Worker、utilityProcess 或独立 Node 子进程的利弊，并给出推荐方案。

该服务未来应能在不重写领域层的情况下：

* 继续内嵌于 Electron；
* 独立安装为学校本地服务器；
* 接入中央服务或同步服务。

二、统一业务入口

学生端 Electron Renderer 不得直接操作 SQLite。

教师端浏览器也不得拥有独立业务实现。

本地学生端通过 IPC 或本地 API 发出的命令，与教师端通过 HTTP/WebSocket 发出的命令，必须汇入同一套：

* Application Service；
* Command Handler；
* 权限校验；
* 状态机；
* SQLite 事务；
* action_log 事件写入；
* 结果投影逻辑。

请明确说明如何避免以下问题：

* IPC 和 HTTP 两套逻辑行为不一致；
* 同一会话被重复完成；
* 平板和一体机同时写入造成竞态；
* 断线重试造成重复答案或重复评分；
* Electron Renderer 绕过权限和状态机直接改库。

三、学生账户与受控会话

学生保留正式账户。

至少需要支持以下会话模式：

* 学生自主完整登录；
* 教师辅助测评；
* 教师辅助学习；
* 教师辅助训练；
* 固定学生工作站模式。

教师在平板选择学生并把任务分配给某台工作站后，学生端应进行低摩擦身份确认，例如：

* 学生头像 + PIN；
* 学生编号 + PIN；
* 学生卡；
* 二维码；
* 教师现场确认后，由学生点击“确认是我”。

教师辅助发起只能创建受限会话，不能让学生端取得该学生账户的全部权限。

请设计 capability 或 session scope，至少区分：

* 查看当前测评；
* 提交当前答案；
* 查看当前学习任务；
* 播放已授权视频；
* 查看本人历史记录；
* 查看教师评语；
* 查看评分规则；
* 管理学生档案。

四、设备模型

不要把系统写死为“一台一体机”。

请设计可扩展的设备注册和工作站模型，至少考虑：

* `device_id`；
* 设备名称；
* 设备角色；
* 所属学校或本地节点；
* 设备配对凭证；
* 信任状态；
* 在线状态；
* 最后心跳时间；
* 当前分配的学生；
* 当前业务会话；
* 设备能力；
* 是否允许学生自主登录；
* 是否启用 Kiosk；
* 是否允许视频播放、摄像头、触摸等能力。

需要明确一个设备、一个学生和一个业务会话之间的并发约束，并禁止同一工作站同时承载两个有效学生会话。

五、测评流程状态

请审查当前 `assessment_session.status` 是否同时承担了业务终态和界面流程阶段。

不要为了双端流程随意扩大原状态枚举。必要时增加独立的 `delivery_phase`、`interaction_phase` 或投影字段，例如：

* PREPARED；
* ASSIGNED；
* STUDENT_CONFIRMATION_REQUIRED；
* ONLINE_IN_PROGRESS；
* ONLINE_COMPLETED；
* WAITING_OFFLINE_OPERATION；
* OFFLINE_SCORING；
* PAUSED；
* COMPLETED；
* REDLINE_HALTED；
* ABORTED。

必须说明哪些是权威业务状态，哪些只是交互阶段投影，避免状态职责混乱。

线上答题和线下实操评分必须属于同一个 `assessment_session`，不得拆成两个相互独立的测评结果。

六、通信协议

建议采用：

* REST/HTTP：创建、分配、提交、评分、暂停、恢复、完成等命令和查询；
* WebSocket 或 SSE：设备在线状态、题目进度、会话阶段变化、安全红线、断线和恢复通知。

实时消息不得成为权威事实来源。客户端收到消息后，必要时必须重新查询服务端状态。

请设计：

* `command_id` 或 `client_event_id`；
* 幂等键；
* 服务端事件序号；
* 客户端最后确认序号；
* 重连后的状态补偿；
* 命令 ACK；
* 乐观并发版本；
* 重复答案和重复评分防护；
* 服务端重启后的会话恢复机制。

七、SQLite 并发与数据一致性

SQLite 只能由本地服务端统一访问。

不得：

* 将 SQLite 文件放到网络共享目录；
* 让教师平板直接访问数据库；
* 让多个终端分别维护数据库副本后临时合并；
* 让 Electron Renderer 直接打开 SQLite；
* 让 HTTP 路由绕过 Repository 和领域服务。

请明确：

* 单写入入口；
* 事务边界；
* WAL 使用边界；
* 写入队列或并发控制；
* 服务异常退出后的恢复；
* Schema Migration；
* 数据备份；
* 数据完整性检查；
* action_log 与 SQLite 投影不一致时的处理原则。

八、安全红线

教师在平板触发安全红线时，必须由服务端完成：

1. 创建 `safety_incident`；
2. 写入 action_log；
3. 批量绑定相关开放会话；
4. 将会话推进为 `REDLINE_HALTED`；
5. 生成 `LEVEL_FAIL_BY_SAFETY`；
6. 阻断普通报告；
7. 通过实时通道通知学生工作站停止当前流程。

学生端和教师端都不能仅通过修改前端状态模拟熔断。

请核对该双端架构是否会破坏现有安全事件生命周期、权限、核心事实冻结、void_reason 和 replacement_incident 规则。

九、局域网发现与安全

教师平板访问本地服务时，不能仅依赖教师手工输入随机 IP。

请评估：

* 固定设备名；
* mDNS/Bonjour；
* 一体机显示配对二维码；
* 短期配对码；
* 本地节点发现；
* IP 变化后的恢复；
* 端口冲突处理。

即使运行在学校局域网，也必须设计：

* 教师身份认证；
* 设备配对；
* 短期访问令牌；
* Token 撤销；
* CORS 白名单；
* CSRF 防护；
* 请求限流；
* 审计日志；
* 不向未授权浏览器暴露学生名单和个人记录；
* Electron `contextIsolation`、关闭 `nodeIntegration`、CSP 等基本安全边界。

请说明局域网 HTTP、HTTPS、自签名证书和未来远程访问的边界，不要把“同一局域网”当成可信认证机制。

十、视频和学习资源

考虑后续学生观看视频、图片、音频和课件。

不要把大型视频二进制直接存入 SQLite。

请设计本地资源服务和资源存储抽象，至少考虑：

* 资源清单；
* hash 或稳定资源 ID；
* 本地文件路径；
* MIME 类型；
* 文件完整性；
* HTTP Range 请求；
* 视频断点播放；
* 缩略图；
* 资源版本；
* 离线资源包；
* 将来从中央服务同步资源。

学生只能访问当前账户或当前任务已授权的资源。

十一、未来学校级与云端同步

当前仍使用本地 SQLite，但请保留本地边缘节点向学校服务器或中央平台同步的演进路径。

请审查是否需要提前引入：

* `node_id`；
* 全局唯一 ID；
* 事件 ID；
* 记录版本号；
* `created_at`、`updated_at`；
* 数据来源节点；
* outbox；
* sync_state；
* 幂等同步键；
* 冲突处理策略。

不要现在实现复杂分布式系统，但也不要使用只能在单机成立、未来无法迁移的自增 ID 和隐式本地假设。

十二、版本兼容与运维

请设计：

* Electron 版本；
* Local Server 版本；
* API 协议版本；
* Schema 版本；
* 教师 Web 前端版本；
* 健康检查接口；
* 启动失败提示；
* 端口占用处理；
* 服务自动重启；
* 优雅关闭；
* 日志轮转；
* 本地诊断信息；
* 数据库备份和恢复；
* 升级失败回滚；
* 教师端与服务端兼容性检查。

教师 Web 最好由同一本地服务直接提供静态资源，以降低前后端版本不一致风险。

十三、技术选型

请结合当前仓库依赖和代码结构，在 Fastify、Express 或其他轻量 TypeScript 服务框架中做出选择并说明原因。

不要只因为 Express 常见就默认选择，也不要为了技术新颖引入过重框架。

重点比较：

* TypeScript 类型支持；
* JSON Schema；
* 请求校验；
* 性能；
* WebSocket 集成；
* 插件复杂度；
* 安全维护；
* 与现有项目的侵入程度。

请在完成仓库审查后，输出以下内容：

1. 方案 B 的最终推荐拓扑图；
