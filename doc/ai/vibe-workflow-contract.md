# Vibe Workflow Contract

本文件是 `/vibe-feature`、`/vibe-impl`、`/vibe-review`、`/vibe-accept` 的共享执行协议。四个命令不得复制维护项目业务不变量，而应读取本文件和 `baseline.yaml` 指向的权威资料。

## 1. 事实来源优先级

发生冲突时，按以下顺序处理：

1. 当前会话中用户的明确指令；
2. 当前目录及上级目录适用的 `AGENTS.md`、`.claude/rules/` 或等价规则；
3. `doc/specs/baseline.yaml` 指向的权威资料；
4. 已批准的功能 PRD、架构决策记录和迁移计划；
5. 当前代码、Schema、测试和 CI 行为；
6. 历史实现文档、任务书和模型推断。

不得因为文件名中含有 `latest`、`final`、较高版本号或修改时间较新，就自行认定其为权威文件。

若 `baseline.yaml` 缺失、指向文件不存在，或同时存在互相冲突的权威定义：

- 不得静默选择其中一份；
- 输出 `BLOCKED`；
- 列出冲突位置和继续所需的最小决策。

## 2. 渐进式上下文加载

不要默认读取整个代码库和所有规格文件。

### 阶段 A：读取索引

至少读取：

- 适用的 `AGENTS.md` / rules；
- `doc/specs/baseline.yaml`；
- `baseline.yaml` 指向的项目不变量；
- 当前任务直接指定的文件。

### 阶段 B：任务分类

将任务标记为一个或多个影响域：

- `UI_UX`
- `DOMAIN_LOGIC`
- `DATABASE_MIGRATION`
- `EVENT_PROJECTION`
- `IPC_API`
- `AUTH_PERMISSION`
- `SAFETY_FSM`
- `RESULT_REPORT`
- `ASSET_CONTENT`
- `DEPLOYMENT_OPERATIONS`

### 阶段 C：按影响域读取

只读取完成判断所需的相关源文件、测试、数据合同和规格章节。发现影响扩大时，再增量读取，不要凭印象继续。

## 3. 风险分级

### R0：低风险

文案、样式、注释、非行为性配置，且不影响权限、数据、接口、路由、状态或构建流程。

### R1：普通功能

单模块内的行为变化，可通过局部测试和局部回归验证。

### R2：跨模块或关键数据流

涉及 IPC/API、权限、持久化写入、事件、结果投影、跨页面流程、外部依赖或兼容性。

### R3：高风险

涉及 Schema、迁移、FSM、安全红线、审计、并发、数据修复、权限模型、不可逆操作、生产发布或核心结果计算。

风险等级由实际影响决定，不由文件数量决定。若存在多个等级，采用最高等级。

## 4. 项目不变量

项目专属约束必须维护在 `baseline.yaml` 指向的 `project-invariants.md` 中，并赋予稳定 ID。

每次任务应列出“本次适用的不变量 ID”，不要在四个 Skill 中重新复述完整规则。

若新发现一个项目专属且可复发的问题，应在 Review 或 Accept 输出中增加“规则沉淀候选”，建议落到以下至少一种机制：

- 项目不变量；
- Schema 或数据库触发器；
- 类型系统；
- lint / 静态检查；
- 单元或集成测试；
- CI 门禁；
- 数据合同或架构决策记录。

## 5. 跨文件登记副作用

凡是“修改 A 必须同步修改 B”的关系，都属于登记副作用，不得仅凭主体任务机械简单而交给低能力子 Agent 后直接采信。

执行前建立副作用登记表，例如：

| 主变更 | 必须同步核验 |
|---|---|
| IPC handler | preload 白名单、shared type、权限校验、IPC 测试 |
| EventType | payload interface、持久化、reducer/projection、回放测试 |
| Schema 字段 | migration、repository、domain type、fixture、兼容测试 |
| 状态迁移 | Schema 触发器、领域服务、权限、异常路径测试 |
| 新路由 | 路由表、权限守卫、导航入口、深链接测试 |
| 新结果字段 | 计算逻辑、投影、报告、导出、历史数据兼容 |

只要存在登记副作用，主循环或高能力 Reviewer 必须执行一次同步核验。

## 6. 证据标准

所有“已完成”“通过”“存在缺陷”的结论必须有证据。

可接受证据包括：

- 文件路径和行号；
- PRD 章节或稳定规则 ID；
- `git diff` 中的具体片段；
- 命令、退出码和关键输出；
- 测试名称及结果；
- 实机操作步骤和观察结果。

不得以以下内容作为唯一证据：

- 子 Agent 的文字总结；
- “看起来正确”；
- 没有测试文件所以视为通过；
- 未执行的人工步骤；
- 未读取完整上下文时的猜测。

## 7. 状态词汇

验收和核验统一使用：

- `PASS`：已执行且证据表明满足要求；
- `FAIL`：已执行且发现明确不满足；
- `NOT_RUN`：本轮未执行；
- `BLOCKED`：因环境、权限、缺失资料或冲突无法执行。

`NOT_RUN` 和 `BLOCKED` 均不得写成通过。

## 8. Reviewer 独立性

Writer 和 Reviewer 应使用不同上下文阶段或独立子 Agent。Reviewer 的职责是独立核验，不是为已有方案辩护，也不是为了满足角色而制造问题。

若平台无法提供独立子 Agent：

- 在新一轮上下文中重新读取工件；
- 明确标记为“非独立自审”；
- R3 任务不得仅凭非独立自审判定完全通过。

## 9. 子 Agent 使用规则

模型选择按能力需求，不按固定模型名称：

- `FAST`：明确、局部、可机械验证的样板工作；
- `REASONING`：跨文件判断、架构、迁移、权限、并发、FSM、安全、结果计算和冲突处理。

存在登记副作用时，即使主体工作属于 `FAST`，也必须由 `REASONING` 角色或主循环完成同步核验。

子 Agent 返回后至少检查：

```bash
git status --porcelain
git diff --stat
git diff --check
```

并读取实际 diff 后再采信其总结。

## 10. 停止条件

出现以下任一情况，停止继续修改并输出当前证据：

- 权威资料缺失或冲突；
- 同一失败命令连续重复三次且没有新证据；
- 连续操作没有产生新的定位、文件差异或测试结果；
- 任务要求与项目不变量冲突；
- 需要删库、破坏性迁移、生产操作或不可逆决策但未获授权；
- 测试或验证环境缺失，无法支撑结论；
- R3 设计仍存在未关闭的 P0。

## 11. 权限边界

除非用户明确授权，不得自动执行：

- 删除或重置数据库；
- 丢弃用户现有改动；
- `git commit`、`git push`、merge、rebase 或强制覆盖；
- 发布、部署或修改生产数据；
- 新增外部服务、付费依赖或敏感权限；
- 扩大已批准功能范围。

## 12. 输出原则

输出必须区分：

- 已确认事实；
- 合理推断；
- 未解决问题；
- 未执行项目；
- 下一步可执行动作。

不得用笼统的“已完成”“应该没问题”代替可核验证据。
