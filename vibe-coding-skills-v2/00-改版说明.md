# Vibe Coding Skills v2 改版说明

## 一、与 Claude 建议重合的部分

本次改版吸收了双方一致确认的结构性问题：

1. 四个文件之间缺少单一事实来源，导致事件写入顺序、IPC 白名单、安全状态机等规则重复维护并发生措辞漂移。
2. 权威 PRD 的具体版本号和章节号不应硬编码在多个 Skill 中。
3. Reviewer 必须给出文件、行号、段落或命令输出等证据，不能只输出抽象判断。
4. `console.log`、注释代码、显式 `any`、Secrets 等可机械判定项，应迁入 lint、脚本或 CI，而不是长期依赖模型人工检查。
5. 项目专属、无法从通用推理得到的约束必须保留；通用工程提醒可以逐步做减法。
6. 子 Agent 的文字汇报不能直接采信，必须核对真实 diff、工作区状态和测试结果。

## 二、Claude 建议中新增并采纳的重点

### 1. 跨文件“登记副作用”

不能只根据任务是否机械来选择弱模型或子 Agent。凡是存在“改 A 必须同步改 B”的登记关系，即使主体代码很简单，也必须增加主循环核验。

典型关系包括：

- IPC handler ↔ preload 白名单 ↔ shared type；
- EventType ↔ payload interface ↔ reducer/projection；
- Schema 字段 ↔ migration ↔ repository/type/test；
- 路由 ↔ 权限守卫 ↔ 导航入口；
- 状态迁移 ↔ Schema 触发器 ↔领域服务 ↔ 回归测试。

本版在共享协议和 `/vibe-impl` 中新增“副作用登记表”。

### 2. 安全原则必须完整传入子 Reviewer

不能假定子 Agent 自动拥有主循环全部上下文。每次调用 Reviewer，都必须显式传入：

- 被审查工件全文或真实 diff；
- 当前权威资料清单；
- 本次适用的不变量 ID；
- 风险等级；
- 特定安全原则和权限边界。

### 3. 实际缺陷应反哺工程规则

每次 Review 或 Accept 捕获到项目专属、可复发的缺陷，应输出“规则沉淀候选”：

- 增加或修订项目不变量；
- 增加自动化测试；
- 增加静态检查；
- 修订数据合同或状态机文档。

这使 Skill 不只是执行清单，也能积累真实踩坑经验。

## 三、本版额外增加的改进

1. 用 `baseline.yaml` 维护当前权威资料指针，避免根据文件名猜版本。
2. 引入 R0–R3 风险分级，避免所有任务使用同等重量流程。
3. 引入渐进式上下文加载，先读索引，再按影响域读取资料。
4. Reviewer 从“只找问题”改为“独立、证据优先、默认怀疑但不制造问题”。
5. 实现步骤按工程原子性拆分，不再使用“最多五个文件”作为硬门槛。
6. 验收结果采用 `PASS / FAIL / NOT_RUN / BLOCKED` 四态，禁止把未执行的人工项目写成通过。
7. 分离步骤验收与合并验收，降低日常迭代成本。
8. 明确禁止 Skill 在未授权情况下自动 commit、push、merge、删库、发布或修改生产数据。
