# /vibe-review — 证据化独立审查

## 目标

对 PRD、实现文档或代码差异进行独立、证据优先的审查。

Reviewer 默认怀疑，但不得为了满足“找问题”的角色而制造问题。没有发现阻断项时，应明确说明通过及其证据。

本命令只审查，不修改被审查工件。

## 输入

```text
/vibe-review prd <path>
/vibe-review impl <path>
/vibe-review code <base>...<head>
```

代码审查优先使用真实 diff，不接受仅凭开发者总结或文件列表判定通过。

## Step 0：加载审查基线

读取：

1. `doc/ai/vibe-workflow-contract.md`；
2. 适用的 `AGENTS.md` / rules；
3. `doc/specs/baseline.yaml`；
4. 被审查工件；
5. 本次适用的权威资料和项目不变量；
6. 风险等级。

确认本轮实际审查范围，并记录未读取、无法读取或不在范围内的内容。

若调用方没有传入关键安全原则、权限边界或不变量 ID，Reviewer 必须自行从权威入口读取，不得假设已有上下文。

## Step 1：证据规则

每条问题必须包含：

- 严重级别；
- 文件路径、行号、段落、规则 ID 或 diff 位置；
- 触发条件；
- 实际影响；
- 为什么违反权威规则或预期行为；
- 最小修复建议；
- 建议回归测试。

无法确认的问题标记为 `NOTE / 待验证`，不得直接定为 P0。

不得：

- 用风格偏好冒充正确性问题；
- 提出与本次范围无关的大重构；
- 因“没有找到问题”而凭空生成缺陷；
- 只看总结，不看真实工件；
- 把未执行测试写成通过。

## Step 2：严重度定义

### P0 — 阻断

会导致或可能导致：

- 数据损坏或不可恢复；
- 安全红线失效；
- 权限越权；
- 核心流程不可用；
- 状态机、事件回放或历史复现错误；
- 迁移不可执行或无法回滚；
- 明确违反权威 PRD 或项目不变量。

必须修复后才能继续。

### P1 — 本轮需修复

存在明确功能缺陷、异常路径遗漏、兼容性问题、测试盲区或较高维护风险，但不满足 P0。

### P2 — 建议

不影响本轮正确性和合并，可提高可维护性、可读性、性能或体验。

### NOTE — 待验证

信息不足、需要实机环境、外部依赖或产品决策，不能作为已确认缺陷。

## Step 3：PRD 审查

至少核验：

1. 问题、目标和成功定义是否一致；
2. 当前行为与目标行为是否有证据；
3. 范围和明确不做是否清楚；
4. 角色、权限和数据可见性；
5. 安全原则及“先熔断后归因”等适用不变量；
6. 并发、重复提交、终态、空数据、异常退出；
7. 三类结果及其他项目专属语义是否被误合并或简化；
8. 数据、事件、IPC/API 和迁移影响；
9. 验收标准是否可执行；
10. 回滚、兼容性和残余风险；
11. 是否存在未经确认的产品决策伪装成技术细节。

## Step 4：实现文档审查

至少核验：

1. 每一步是否有单一目标、完成状态和回滚方式；
2. 步骤依赖和顺序是否正确；
3. 中间状态是否仍可构建、可验证；
4. 跨文件副作用登记是否完整；
5. 事件、Schema、IPC、路由、权限和结果链是否同步；
6. 测试是否覆盖正常、异常、边界、并发、失败恢复；
7. 测试是否验证行为而非实现细节；
8. 是否存在大而无边界的“顺手重构”；
9. R3 风险是否具有独立审查和人工验收；
10. 计划是否与当前代码实际结构一致。

文件数量只作为观察信号，不作为单独判错依据。

## Step 5：代码审查

### 5.1 获取真实范围

优先读取：

```bash
git status --short
git diff --stat <base>...<head>
git diff --check <base>...<head>
git diff <base>...<head>
```

同时读取新增或修改的测试、相关完整函数上下文和验证命令输出。

### 5.2 审查维度

- 正确性与异常处理；
- 权限和输入验证；
- 事务、幂等和并发；
- 状态机与事件顺序；
- 跨文件登记副作用；
- Schema、migration 和历史兼容；
- IPC/preload/renderer 边界；
- 类型安全和 JSON contract；
- Secrets、敏感日志和数据泄露；
- 资源释放和性能退化；
- UI 可访问性和错误恢复；
- 无关修改、生成文件和依赖变化；
- 测试是否能发现错误实现；
- 是否遗漏权威不变量。

可机械判定的 `no-console`、显式 `any`、Secrets 等，应优先引用 lint 或静态检查结果；不要仅靠肉眼断言。

| 检查 | 状态 | 证据 |

- 位置：

## Step 7：结论规则

- 存在 P0：`BLOCKED`；
- 无 P0，但存在未关闭 P1：`CONDITIONAL_PASS`；
- P0/P1 清零，必需检查有证据：`PASS`；
- 关键范围未审查或 R3 仅做非独立自审：不得给出完全 `PASS`。
