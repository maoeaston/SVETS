# /vibe-impl — PRD 转原子实施计划

## 目标

把已批准的 Mini-PRD 转换为可逐步实现、逐步验证、可独立回滚的实施文档。

本命令默认只生成计划。只有用户明确要求继续执行时，才进入逐步编码。

## 输入

```text
/vibe-impl <approved-prd-path>
```

## Step 0：前置校验

读取：

1. `doc/ai/vibe-workflow-contract.md`；
2. 适用的 `AGENTS.md` / rules；
3. `doc/specs/baseline.yaml`；
4. 指定 Mini-PRD；
5. PRD 引用的权威资料和项目不变量。

确认：

- PRD 状态允许进入实现；
- 没有未关闭的 P0；
- 权威路径有效；
- 风险等级已记录；
- 范围和明确不做项清楚。

否则输出 `BLOCKED`。

## Step 1：读取相关实现上下文

按 PRD 影响域渐进式读取：

- 现有领域服务和 repository；
- shared types；
- IPC/API、preload 和权限守卫；
- Vue 路由、视图和状态管理；
- Schema、migration、trigger；
- 相邻测试、fixture 和 CI 命令。

不要只根据 PRD 中的建议文件列表制定计划；必须核对当前代码实际结构。

## Step 2：建立变更地图

输出：

### 2.1 当前到目标的状态变化

- 现状；
- 目标；
- 迁移路径；
- 失败恢复路径。

### 2.2 变更依赖图

列出步骤间的真实前置关系。

### 2.3 跨文件副作用登记表

至少检查：

| 主变更 | 同步登记或核验 |
|---|---|
| IPC handler | preload 白名单、shared type、权限、测试 |
| EventType | payload、validator、persist、reducer/projector、回放测试 |
| Schema | migration、repository、type、fixture、兼容测试 |
| 状态迁移 | trigger、领域服务、权限、异常路径 |
| 路由 | router、guard、navigation、deep link |
| 结果字段 | 计算、projection、report、export、历史兼容 |

若无此类副作用，明确写 `NONE`。

## Step 3：拆分原子实施步骤

每一步以“单一工程目标”为边界，不使用固定文件数量作为硬门槛。

一个步骤必须同时满足：

1. 目标单一；
2. 可独立构建或验证；
3. 失败后可单独回退；
4. 不混入无关重构；
5. 完成状态可通过证据判断；
6. 不让仓库长期处于无法构建的中间状态。

大 diff 应按责任边界拆分，但修改 6–10 个强关联文件不自动视为步骤过大。

## Step 5：测试强度

### R0

- 定向 lint / typecheck；
- 视觉或文案核验；
- 无需为无行为变化强行增加复杂测试。

### R1

- 相关单元测试；
- 定向构建或组件测试；
- 核心路径冒烟。

### R2

- 单元 + 集成；
- 跨文件登记同步测试；
- 权限、异常退出、重复提交、兼容性。

### R3

- 状态机、并发、故障注入、迁移、回滚、历史数据兼容；
- 安全和权限负向测试；
- 独立 Review；
- 必要人工验收不得省略。

## Step 6：Reviewer 审查

调用：

```text
/vibe-review impl <impl-path>
```

显式传入 PRD、实现文档、适用不变量、风险等级和已读取代码范围。

Reviewer 重点核验：

- 依赖关系和步骤顺序；
- 跨文件登记副作用是否遗漏；
- 测试能否杀死错误实现；
- 中间 commit 是否可构建、可回退；
- 是否违反权威 PRD 或项目不变量；
- 是否把 R3 风险降级成普通机械任务。

最多两轮。仍有 P0 时输出 `BLOCKED`。

## Step 7：执行阶段规则

仅在用户明确要求实施时执行。

### 7.1 模型/子 Agent 分工

- `FAST`：样板、明确映射、局部且可机械验证的改动；
- `REASONING`：跨文件判断、架构、迁移、权限、并发、FSM、安全、结果计算。

只要存在跨文件登记副作用，即使主体实现简单，也必须由主循环或 `REASONING` 角色进行同步核验。

### 7.2 每步闭环

每完成一步：

1. 查看真实 diff；
2. 核对副作用登记表；
3. 运行 `/vibe-accept step <step-id>`；
4. 记录 `PASS / FAIL / NOT_RUN / BLOCKED`；
5. 未通过不得进入下一步，除非实现文档明确允许并记录原因。

### 7.3 子 Agent 结果核验

至少运行：

```bash
git status --porcelain
git diff --stat
git diff --check
```

必须读取实际变更后再采信总结。

### 7.4 冲突处理

按共享协议的事实来源优先级解决。

- 能根据权威来源直接解决：直接修正并记录；
- 任务书陈旧：更新任务书，不迁就旧文字；
- 涉及范围、数据损失、权限或不可逆决策：请求用户决策；
- 无法解决：输出 `BLOCKED`。

不得一遇到普通实现分歧就把问题抛给用户。

## Step 8：输出

输出实现文档路径、步骤数量、风险等级、关键副作用登记项、Reviewer 结论，以及是否具备开始实施的条件。

不得自动 commit、push、merge 或发布。
